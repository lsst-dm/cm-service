# Known Issues

## ORM model drift

The ORM models in `lsst.cmservice.models.db` do not exactly describe the schema
that the migrations build. The migrations are the source of truth for the
database. In every known case the database is stricter or more specific than
the models.

Running `alembic check` against a database migrated to head (revision
`8217594f8818`) reports the differences below. None of them affects how the
application behaves at runtime.

### Impact

**Do not trust `alembic revision --autogenerate` output as-is.** An
autogenerated revision would try to make the models' view of the schema true:
it would loosen `NOT NULL` columns, drop unique constraints, and drop the
partial index that enforces a single default manifest per campaign and kind.
Review and prune any autogenerated revision by hand, or write revisions
manually.

### Columns that are nullable in the models but `NOT NULL` in the database

These columns are declared with an explicit `sa_column=Column(...)` without
`nullable=False`, through `jsonb_column()` or directly. SQLModel does not infer
nullability from the type annotation when it is given a `Column`, so the model
column is nullable.

| Table | Columns |
|---|---|
| `activity_log_v2` | `created_at`, `detail`, `from_status`, `metadata`, `notification_labels`, `to_status` |
| `audit_log_v2` | `action`, `context`, `object_type` |
| `campaigns_v2` | `configuration`, `metadata`, `status` |
| `edges_v2` | `configuration`, `metadata` |
| `machines_v2` | `state` |
| `manifests_v2` | `kind`, `metadata`, `spec` |
| `nodes_v2` | `configuration`, `kind`, `metadata`, `status` |
| `notification_labels_v2` | `configuration`, `kind` |
| `schedules_v2` | `configuration`, `metadata` |
| `tasks_v2` | `created_at`, `metadata`, `status` |
| `templates_v2` | `kind`, `metadata` |

Fix: pass `nullable=False` to these `Column` objects, including the one built
in `jsonb_column()`.

### Column that is required in the model but nullable in the database

- `audit_log_v2.request_id`: the model declares `request_id: UUID`, but the
  column was created nullable.

Fix: decide which is intended. If audit entries can be written outside a
request, make the model `UUID | None`. Otherwise add a migration to set the
column `NOT NULL`.

### Constraints and indexes that exist only in the database

The models do not declare these, so the ORM does not know about them.
`create_all()` (used by the test suite) does not create them.

| Table | Object | Definition |
|---|---|---|
| `campaigns_v2` | `campaigns_v2_name_namespace_key` | unique (`name`, `namespace`) |
| `nodes_v2` | `nodes_v2_name_version_namespace_key` | unique (`name`, `version`, `namespace`) |
| `edges_v2` | `edges_v2_source_target_namespace_key` | unique (`source`, `target`, `namespace`) |
| `manifests_v2` | `manifests_v2_name_version_kind_namespace_key` | unique (`name`, `version`, `kind`, `namespace`) |
| `templates_v2` | `uq_schedule_name_kind_version` | unique (`schedule_id`, `kind`, `name`, `version`) |
| `manifests_v2` | `ix_manifest_single_default` | unique btree (`namespace`, `kind`) `WHERE "default" IS TRUE` |
| `audit_log_v2` | `ix_audit_log_context` | gin (`context` `jsonb_path_ops`) |

Because the tests build their database with `create_all()`, they run without
these guarantees. For example, the test database allows duplicate campaign
names within a namespace, and more than one default manifest per kind.

Fix: declare these in each model's `__table_args__`, using the same names as
the database objects. Note that a model's `__table_args__` replaces the
`{"schema": ...}` set on `BaseSQLModel`. That is currently harmless because
the shared `MetaData` also carries the schema, but `Schedule` already relies on
it.

### `TEXT` columns that the models map to `VARCHAR`

These are plain `str` fields, which SQLModel maps to `AutoString`
(`VARCHAR`). The migrations created them as `TEXT`.

- `audit_log_v2`: `actor`, `object_name`
- `notification_labels_v2`: `name`
- `schedules_v2`: `cron`, `name`
- `templates_v2`: `manifest`, `name`

In PostgreSQL an unbounded `VARCHAR` and `TEXT` behave the same, so this
difference only shows up in autogenerate. Fix: declare these fields with
`sa_type=Text`.

## Reproducing

Migrate an empty schema to head, then compare it with the models:

```sh
export DB__URL=postgresql://cm-service@localhost:${PGPORT}/cm-service
export DB__PASSWORD=INSECURE-PASSWORD
export DB__PORT=${PGPORT}
export DB__TABLE_SCHEMA=cm_drift_check

alembic -x schema=cm_drift_check upgrade head
alembic -x schema=cm_drift_check check
```

`PGPORT` is the local compose database port
(`docker compose port postgresql 5432`). Drop the `cm_drift_check` schema
afterwards. When every item above is fixed, `alembic check` reports
`No new upgrade operations detected.`
